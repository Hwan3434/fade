# fade

[한국어](README.md) · [English](README.en.md) · [中文](README.zh.md)

Claude Code 専用のスキルプラグインです。Claude デスクトップアプリ（Code タブ）と Claude CLI で使います。ほかのエージェントを使う人は、スキルを読んで自分の環境に合わせて書き換えてください。機能を増やすためではなく、縮んでいくために作ったツールです。
モデルが賢くなるほど文章を消し、最後には 0 行になることを目指しているので、名前は fade です。縮むのは文章です。プロセスを守る仕組み（スクリプト、フック、テスト）は残ります。

## なぜ作ったのか

### 究極の目標

> 究極的には、このスキルが要らなくなる日を願っている。最小化する目的そのものが、AI が賢くなってわざわざ説明しなくてもよくなる日を願うことであり、AI が賢くなったという前提のもとで、私たちは引き算の美学を進めている。

### AI を信じるということ

> AI を信じるということは毎日変わる。新しいモデルが出るたびに。ただし AI を信じるとは、AI への説明を最小限にするということであって、静的検査、フック、リント、テストをしないということではない。これらは必須であり、その上でエージェントが前に進もうと後ろに戻ろうと、右に曲がろうと左に曲がろうと、それを信じるということだ。

### このツールの立ち位置

> ちゃんと作れないなら代わりに作ってあげず、開発者に作ってもらおう。私たちは、そうして開発者が作ったものの上で AI を制御するためのツールだ。静的検査のレイヤーには関わらない。

### 捨てた道

> 文章でエージェントを制御しようとすること。核心はこれだ。

## どう作ったのか

- リポジトリを守る仕事（静的検査、hook、リント、テスト、検証手段）はそのリポジトリが担います。fade はその上でリードとワーカーが働くやり方だけを持ちます。
- その働き方も、文章より仕組みで守ります。`job` の段階記録は、スクリプト（`job.py`）がテストコマンドを自分で実行して確かめたものだけを残し、マージの直前にフックがその記録と CI を確認します。fade が載せる仕組みは、特定のリポジトリに関係しない fade 自身の作業形式と、どのセッションでも取り返しのつかないコマンドをいくつか止めるフック一つだけです。
- 文章で守らせられるルールでも、検査で防げるならスキルから外して検査に回します。回す先はまずそのリポジトリの検査で、人によって違うものはその人の設定です。スキルに残るのはプロセスだけです。
- そのため、検査が揃ったリポジトリでしかうまく動きません。人のいないところで動く `nonstop` は、リポジトリが確認を求める操作を拒むことでしか止まらないので、検査のないリポジトリではその操作を止めるものがありません。
- リポジトリごと、人ごとに違う値（base ブランチ、マージ方式、ブランチ名、検証方法）は書きません。そのリポジトリのルールとその人の設定が決め、モデルはそれを読んで従います。
- 行を足すのは、その行が防ぐ失敗が実際のセッションで確認されたときだけです。モデルが元からやることを書いた行は消します。
- 複数のリポジトリで同じ本文のまま使うものだけを入れます。Claude デスクトップアプリと CLI で条件を満たす方法まで書きます。

## どこへ向かうのか

- 新しいモデルが出るたびに、行を一つずつ消してみます。モデルがその行なしでもこなせたら、その行は二度と戻りません。
- 行が増えるのは失敗が確認されたときだけです。増えた行も、いずれ消す候補です。
- 使わなくなった仕組みも消します。ただし、モデルが良くなったという理由だけで検査を消すことはしません。
- スキルが一つずつ消え、最後の一行まで消えたとき、それがこのプラグインの完成です。

## スキル

- `job`: 仕事の最小単位。計画書を一つ受け取り、テストを先に書き、実装、証拠、実際に使ってみる確認、止める指摘がなくなるまで繰り返すコードレビューのあと、PR、マージ、報告までやり切ります。レビューはバグの軸を必ず回し、仕様の軸も回すかどうかは行数のような固定の基準ではなく、レビューする側が変更の性質（完了基準をいくつも触るか、動作を変えるか文だけか、マージ条件やフックのように間違えると黙って壊れる場所か、一度で読み切れる大きさか）を見て自分で判断します。回さなかったときはその理由をレビューの記録に残します。修正したあとは、修正した部分だけをもう一度レビューし、修正したパスに依存する証拠と使ってみた記録だけをやり直します。レビューが回っている間は止める指摘だけを直し、軽微な指摘は止める指摘がなくなってからまとめて一つのコミットで直して、そのコミットだけをバグの軸で見ます。レビュアーやテスターのようなエージェントの答えは、ターンを終えずに待ちます。解決できないときやユーザーの判断が必要なときは、そこで止まって報告します。ユーザーが「PR まで」のように範囲を狭めたら、その分だけやります。ユーザーに尋ねたことは記録に残し、答えをもらえていない質問は次の報告の先頭に番号付きで書き直します。
- `try`: `tester` エージェントを起動して成果物をユーザーが使う通りに使ってもらい、ケースごとに画面とログを残します。
- `harden`: AI がしたミスを、指示に文章を足すのではなく検査（リント、テスト、フック、権限設定）で防ぎます。
- `grill`: 実行前に残っている決定を、番号と推奨回答を付けて最後まで尋ねます。
- `dispatch`: コード変更を、リポジトリのワークツリーで動く新しいセッション（ワーカー）に `job` の計画書で任せ、ワーカーが添えた証拠を完了基準と照らし合わせます。デスクトップアプリではセッションツールで、CLI では `claude -p` で起動します。ワーカーのモデルは、ユーザーが今回指定した値、なければユーザーの指示ファイルにある値に決めて起動し、どちらもなければリードのモデルを引き継ぐことを起動前に知らせます。起動する前に新しいサブエージェントで計画書の抜けを探し、ワーカーが終わったら `hardener` の検査提案をユーザーに伝えます。PR がマージされるか閉じられたら、尋ねずにワーカーのワークツリー、マージされた作業ブランチ、ワーカーのセッションを片付けます（コミットされていない変更やリモートにないコミットがあれば消しません）。動いている最中のワーカーには基準を足すメッセージを送りません。そのワーカーの前のターンの報告通知が消えるからです。それでも話しかけた場合は、直前の報告の全文を探してユーザーに伝えます。
- `debug`: 失敗するコマンドを一つ作るところから始め、決まった順序でバグを診断します。
- `nonstop`: 見守る人なしにタスクリストを最後まで回し、タスクごとに `job` を実行します。ユーザーが直接呼んだときだけ使います。タスクがマージされるたびに、`dispatch` の後片付けと同じ確認を経て、そのタスクのワークツリーとブランチを消します。PR までのタスクと、保留やブロックされたタスクは残します。

## エージェント

スキルが起動するサブエージェントです。定義は `agents/` にあります。モデルは決めません。使う人が選んだモデルで動きます。

- `reviewer`: `job` の仕様の軸のレビュアー。実装者の報告を信じず、計画書と diff を一つずつ照らし合わせ、仕様を満たしているか（抜け、やりすぎ、取り違え）を先に、テストの質を次に見ます。指摘ごとに止める指摘か些細な指摘かを書きます。ツールは読み取り（Read、Grep、Glob）だけです。
- `tester`: 成果物をユーザーのように使ってみて、報告だけをします。シナリオを先に書き、画面と出力はワークツリーの git フォルダの中の `fade-try/` に残します。編集ツール（Edit、Write、NotebookEdit）を外しています。
- `hardener`: 終わった作業のミスをミス記録の中で key ごとにまとめ、同じ key が二回以上あるか誰にでも起きるミスなら、`harden` の順序で検査の提案を作ります。提案だけで、直しはしません。

## 仕組み

- `skills/job/job.py`: `job` の段階記録。実装前の失敗（red）と実装後の成功（green）は、コマンドを自分で実行して確かめたものだけを残します。証拠と実際に使ってみた記録は、ファイルがあるときだけ残ります。マージ条件の green とレビューは今のコミットで取ったものだけを数えます。証拠と使ってみた記録は、依存するパス（`--paths`）を書いておけば、取ったコミットのあとでそのパスが変わらないかぎり有効で、書かなければ今のコミットで取ったものだけを数えます。`review-files` は仕様レビュアーを呼ぶか判断する材料として、base との diff の行数と変わったファイルの数と一覧を知らせ、二回目のレビューからは、仕様レビュアーが最後に見たコミットのあとに修正した部分だけをレビュアー用のファイルに書きます。`review --minor` は、軽微な指摘をまとめて直した一つのコミットをバグの軸で見たレビューを残し、マージ条件のレビューとして数えます。`review --spec` は仕様レビュアーも見たレビューで、`--spec` も `--minor` もないレビューは、仕様レビュアーを呼ばなかった理由を要約に書かないと残りません。オプションはほかの引数の前後どちらに書いても読み（後ろの引数をすべてパスとして受け取る `--paths` は最後に書きます）、知らないオプションはどのコマンドでも受け付けません。`--` で始まる一語をタイトルや理由のような値として渡すときは、その前に `--` を別に置きます。元に戻せるか（`door`）を残さないとマージできず、一方通行のドア（元に戻せない）ならマージはユーザーが決めます。`show` の一行目は状態で、既定の出力は完了基準ごとに一行です。コマンドの全文とログは `show --full` で出ます。記録はワークツリーの git フォルダの中にあり、コミットされません。`ask` はユーザーに尋ねたことを残し、`answered` はもらった答えを書きます。答えのない質問は `show` の状態行のすぐ下に番号付きで出ます。
- `hooks/merge_gate.py`: `gh pr merge` の直前に、そのワークツリーの `job` 記録と CI、PR の最新コミットが検証したローカルの HEAD と同じかを確認します。抜けがあるか「PR まで」の作業なら、マージを止めて理由を伝え、ミス記録に残します。`job` の記録がない場所では何もしません。ミスを防ぐ手すりであって、セキュリティの境界ではありません。
- `hooks/permission_gate.py`: 人のいない `job`（`job.py start --unattended`）で承認ダイアログが出ようとすると、待たずに拒否します。止められた作業が完了基準に欠かせないものなら、止まった場所を報告して終わり、脇道の作業ならそれを外して続けます。拒否したらミス記録に残します。それ以外のセッションでは何もしません。
- `hooks/destructive_gate.py`: **fade を入れたすべてのセッションの Bash 呼び出しにかかります。** `job` と関係なくセッションの動きを変える、fade で唯一のフックです。ルート、ホームとその上のフォルダ、`~/.ssh` の再帰削除、既定ブランチ（main、master、そのリポジトリの既定ブランチ）への force push、デバイスに書き込む `dd`、`mkfs` を拒否します。引用された文字と heredoc の本文はコマンドとして扱いません。止めるだけで許可はせず、どうしても必要なコマンドはユーザーがターミナルで直接打ちます。止めたいときは fade プラグインを無効にします。
- ミス記録 `~/.claude/fade/mistakes.jsonl`: リポジトリと作業をまたいで集まるミスが一行に一つずつ溜まります。マージのフックと承認ダイアログのフックが止めたとき、`job.py stop`、`job.py slip`（レビューで直した止める指摘、CI の失敗、ユーザーの指摘）が書き、`hardener` が key と処理を書き込みます。環境変数 `FADE_MISTAKES` でパスを変えられます。
- `tests/`: 上のスクリプトとフック、エージェント定義、`nonstop.py` のテスト。PR ごとに GitHub Actions で動きます。

## インストール

```bash
claude plugin marketplace add Hwan3434/fade
```

```bash
claude plugin install fade@fade
```

デスクトップアプリは同じ設定を読むので、CLI で一度インストールすれば両方で使えます。Claude のクラウドセッションはプラグインを読み込みません。クラウドで使うリポジトリには、スキルフォルダのコピーを `.claude/skills/` に置きます。

## 参考にしたもの

- [mattpocock/skills](https://github.com/mattpocock/skills): `grill` は `grilling` から、`debug` は `diagnosing-bugs` から出発しました。`code-review` の仕様の軸は `reviewer` の仕様の確認に、`tdd` のテストの基準（期待値は独立した定数にし、自分のモジュールをモックにしない）は `reviewer` のテストの質に、`retro` は `hardener` に、`pr` の Merge Danger（一方通行のドアか双方向のドアか、影響範囲）は `job.py door` に取り入れました。
- [obra/superpowers](https://github.com/obra/superpowers): `subagent-driven-development` のレビュアー（実装者の報告を信じず diff で確かめる）は `reviewer` に、`brainstorming` の builder check は `dispatch` の計画書の抜けの検査に取り入れました。
- [garrytan/gstack](https://github.com/garrytan/gstack): `careful` は破壊的コマンドを止めるフックに、`qa-only` は `tester` に、`land-and-deploy` の PR コミットの照合はマージのフックに取り入れました。
- [cursor/plugins](https://github.com/cursor/plugins) の `pstack`: 検査を載せないやり方。
- [poteto/verification-skill-example](https://github.com/poteto/verification-skill-example): 検証スキルのお手本。
