# fade

[English](README.en.md) · [日本語](README.ja.md) · [中文](README.zh.md)

Claude Code 전용 스킬 플러그인이다. Claude 데스크톱 앱(Code 탭)과 Claude CLI 에서 쓴다. 다른 에이전트를 쓰는 사람은 스킬을 읽고 자기 환경에 맞게 고쳐 쓰면 된다. 기능을 늘리려고 만든 도구가 아니라, 줄어들려고 만든 도구다.
모델이 똑똑해질수록 글을 지워 결국 0줄이 되는 것이 목표라 이름이 fade 다. 줄어드는 것은 글이다. 과정을 지키는 구조(스크립트, 훅, 테스트)는 남는다.

## 왜 만들었나

### 궁극적인 목표

> 궁극적으로는 이 스킬이 필요 없어질 때를 바란다. 최소화하는 목적 자체가 AI 가 똑똑해져서 굳이 설명하지 않아도 될 때를 바라는 것이고, AI 가 똑똑해졌다는 전제하에 우리는 덜어냄의 미학을 진행하고 있다.

### AI 를 믿는다는 것

> AI 를 믿는다는 것은 매일 바뀐다. 새 모델이 나올 때마다. 다만 AI 를 믿는 것은 AI 에게 설명을 최소화한다는 것이지 정적 검사, 훅, 린트, 테스트를 하지 않는다는 것이 아니다. 이것들은 필수이고, 그 위에서 에이전트가 앞으로 가든 뒤로 가든 우회전하든 좌회전하든 그것을 믿는다는 것이다.

### 이 도구의 자리

> 제대로 못 만들면 만들어 주지 말고 개발자들이 만들라고 하자. 우리는 그렇게 개발자들이 만든 것 위에서 AI 를 통제하기 위한 도구다. 정적 검사 레이어 쪽은 관여하지 않는다.

### 버린 길

> 글로써 에이전트를 통제하려고 하는 것. 핵심은 이것이다.

## 어떻게 만들었나

- 레포를 지키는 일(정적 검사, hook, 린트, 테스트, 검증 수단)은 그 레포가 맡는다. fade 는 그 위에서 리드와 워커가 일하는 방식만 담는다.
- 그 일하는 방식도 글보다 구조로 지킨다. `job` 의 단계 기록은 스크립트(`job.py`)가 테스트 명령을 직접 돌려 확인한 것만 남기고, 병합 직전에 훅이 그 기록과 CI 를 본다. fade 가 싣는 구조는 레포와 상관없는 fade 자신의 작업 형식과, 어느 세션에서나 되돌릴 수 없는 명령 몇 가지를 막는 훅 하나다.
- 글로 막을 수 있는 규칙이라도 검사로 막을 수 있으면 스킬에서 빼고 검사로 보낸다. 보낼 곳은 그 레포의 검사가 먼저이고, 사람마다 다른 것은 그 사람의 설정이다. 스킬에 남는 것은 과정뿐이다.
- 그래서 검사가 갖춰진 레포에서만 제대로 돈다. 사람 없이 도는 `nonstop` 은 레포가 확인을 요구하는 일을 거부하는 것으로만 멈추므로, 검사가 없는 레포에서는 그 일을 막을 것이 없다.
- 레포마다, 사람마다 다른 값(base 브랜치, 병합 방식, 브랜치 이름, 검증 방법)은 적지 않는다. 그 레포의 규칙과 그 사람의 설정이 정하고, 모델은 그것을 읽고 따른다.
- 줄을 더하려면 그 줄이 막는 실패가 실제 세션에서 확인되어야 한다. 모델이 원래 하는 일을 적은 줄은 지운다.
- 여러 레포에서 같은 본문으로 쓰는 것만 담는다. Claude 데스크톱 앱과 CLI 에서 조건을 채우는 방법까지 적는다.

## 어디로 가나

- 새 모델이 나올 때마다 줄을 하나씩 지워 본다. 모델이 그 줄 없이도 해내면 그 줄은 다시 돌아오지 않는다.
- 줄이 늘어나는 것은 실패가 확인되었을 때뿐이다. 늘어난 줄도 언젠가 지울 후보다.
- 구조도 쓰지 않게 되면 지운다. 다만 모델이 좋아졌다는 이유만으로 검사를 지우지는 않는다.
- 스킬이 하나씩 사라지고 마지막 줄까지 지워지면, 그때가 이 플러그인이 완성되는 때다.

## 스킬

- `job`: 업무의 최소 단위. 계획서 하나를 받아 테스트를 먼저 쓰고, 구현, 증거, 직접 써 보기, 코드 리뷰를 막는 지적이 없을 때까지 되풀이한 뒤 PR, 병합, 보고까지 끝낸다. 리뷰는 버그 축을 늘 돌리고, 명세 축도 돌릴지는 줄 수 같은 고정 기준이 아니라 리뷰하는 쪽이 변경의 성격(완료 기준을 여럿 건드리는가, 동작을 바꾸는가, 틀리면 조용히 잘못되는 자리인가, 한 번에 읽히는 크기인가)을 보고 스스로 판단한다. 띄우지 않았으면 그 이유를 리뷰 기록에 남긴다. 버그 축은 `job.py review-files` 가 쓴 `bug.patch`(첫 리뷰는 테스트와 글까지 base 와의 전체, 다시 하는 리뷰는 받은 앞 리뷰 뒤)를 끝까지 읽는다. 지적은 계획서와 대조해, 계획서가 정한 것을 뒤집자는 지적은 고치지 않고 「결정과 어긋남」으로 적고, 그 결정이 틀렸다고 보이면 보고의 「결정이 필요한 것」에 올린다. 고친 뒤에는 고친 부분만 다시 리뷰하고, 고친 경로에 기대는 증거와 써 보기만 다시 한다. 리뷰가 도는 동안에는 막는 지적만 고치고, 사소한 지적은 막는 지적이 없어진 뒤 모아서 한 커밋으로 고친 다음 그 커밋만 버그 축으로 본다. 리뷰어와 테스터 같은 에이전트의 답은 턴을 끝내지 않고 기다린다. 해결하지 못하거나 사용자 결정이 필요하면 거기서 멈추고 보고한다. 사용자가 「PR 까지만」처럼 범위를 줄이면 그만큼만 한다. 보고에는 기록 전문을 다시 쓰지 않고, 첫 줄에 PR 에 단 기록 댓글의 주소(PR 이 없거나 댓글이 실패하면 기록 파일의 경로)를 쓴다. 사용자에게 물은 것은 기록에 남기고, 답을 받지 못한 질문은 그 주소 다음에 번호째 다시 적는다. PR 본문은 사람이 읽는 요약(결과, 되돌릴 수 있는가, 고른 것과 이유 중 중요한 것, 고치지 못한 것, 완료 기준마다 한 줄)이고, 기록 전문은 붙이지 않는다. 커밋은 끝에 한 번이 아니라 실패하는 테스트, 구현, 막는 지적 고침처럼 뜻이 갈리는 단계마다 나누고, 메시지에 무엇을 왜 바꿨는지 쓴다.
- `try`: `tester` 에이전트를 띄워 결과물을 사용자가 쓰는 방식 그대로 써 보게 하고, 경우마다 화면과 로그를 남긴다.
- `harden`: AI 가 한 실수를 지침에 글로 더하지 않고 검사(린트, 테스트, 훅, 권한 설정)로 막는다.
- `grill`: 실행 전에 남은 결정을 번호와 권장 답을 붙여 끝까지 묻는다.
- `dispatch`: 코드 변경을 레포의 워크트리에서 도는 새 세션(워커)에 `job` 계획서로 맡기고, 워커가 PR 이나 기록 파일에 남긴 증거를 완료 기준과 대조한다. 데스크톱 앱에서는 세션 도구로, CLI 에서는 `claude -p` 로 띄운다. 워커 모델은 사용자가 이번에 말한 값, 없으면 사용자 지침 파일의 값으로 정해서 띄우고, 둘 다 없으면 리드의 모델을 물려받는다고 띄우기 전에 알린다. 띄우기 전에 새 서브에이전트로 계획서의 빈칸을 찾고, 워커가 끝나면 `hardener` 의 검사 제안을 사용자에게 옮긴다. PR 이 병합되거나 닫히면 묻지 않고 워커 워크트리, 병합된 작업 브랜치, 워커 세션을 정리한다(커밋 안 된 변경이나 원격에 없는 커밋이 있으면 지우지 않는다). 도는 중인 워커에는 기준을 더하는 메시지를 보내지 않는다. 그 워커의 앞 턴 보고 알림이 사라지기 때문이다. 그래도 말을 걸었으면 직전 보고 전문을 찾아 사용자에게 옮긴다.
- `debug`: 실패하는 명령 하나부터 만들고 정해진 순서로 버그를 진단한다.
- `nonstop`: 지켜보는 사람 없이 작업 목록을 끝까지 돌며 작업마다 `job` 을 수행한다. 사용자가 직접 부를 때만 쓴다. 작업이 병합될 때마다 `dispatch` 의 정리와 같은 검사를 거쳐 그 작업의 워크트리와 브랜치를 지운다. PR 까지만인 작업과 보류되거나 막힌 작업은 남긴다.

## 에이전트

스킬이 띄우는 서브에이전트다. 정의는 `agents/` 에 있다. 모델은 정하지 않는다. 쓰는 사람이 고른 모델로 돈다.

- `reviewer`: `job` 의 명세 축 리뷰어. 구현자의 보고를 믿지 않고 계획서와 diff 를 하나씩 대조해 명세 충족(빠진 것, 넘친 것, 잘못 이해한 것)을 먼저, 테스트 품질을 다음에 본다. 지적마다 막는 지적인지 사소한 지적인지를 적는다. 도구가 읽기(Read, Grep, Glob)뿐이다.
- `tester`: 결과물을 사용자처럼 써 보고 보고만 한다. 시나리오를 먼저 적고, 화면과 출력은 워크트리의 git 폴더 안 `fade-try/` 에 남긴다. 레포 밖 임시 폴더의 파일은 지워질 수 있어 `job.py` 가 증거로 받지 않는다. 편집 도구(Edit, Write, NotebookEdit)를 뺐다.
- `hardener`: 끝난 작업의 실수를 실수 기록에서 key 로 묶고, 같은 key 가 두 번 이상이거나 누구에게나 날 실수면 `harden` 의 순서대로 검사 제안을 만든다. 제안만 하고 고치지 않는다.

## 구조

- `bin/`: 플러그인이 켜져 있으면 Claude Code 가 이 폴더를 Bash 도구의 PATH 에 둔다. `job.py` 와 `nonstop.py` 를 경로 없이 부르게 하는 입구가 있고, 본체는 `skills/` 아래에 있다.
- `skills/job/job.py`: `job` 의 단계 기록. 구현 전 실패(red)와 구현 후 통과(green)는 명령을 직접 돌려 확인한 것만 남긴다. red 는 실패 출력의 끝을 찍고, green 은 red 뒤에 내용이 바뀐 파일이 없으면 받지 않는다(구현이 red 전에 이미 있었거나 레포 밖이 바뀌어 통과한 것). 구현이 red 전에 커밋돼 있었거나 테스트만 고쳐 통과시킨 것은 어느 파일이 테스트인지 레포마다 달라 가르지 못한다. 증거와 직접 써 보기는 파일이 있어야 남는다. 병합 조건의 green 과 리뷰는 지금 커밋에서 찍힌 것만 친다. 증거와 써 보기는 기대는 경로(`--paths`)를 적으면 찍은 커밋 뒤로 그 경로가 바뀌지 않는 동안 유효하고, 적지 않으면 지금 커밋에서 찍힌 것만 친다. `review-files` 는 명세 리뷰어를 띄울지 판단할 재료로 base 와의 diff 의 줄 수, 바뀐 파일 수와 목록을 알리고, 두 번째 리뷰부터는 명세 리뷰어가 마지막으로 본 커밋 뒤에 고친 부분만 리뷰어에게 줄 파일로 쓴다. `review --minor` 는 사소한 지적을 모아 고친 커밋 하나를 버그 축으로 본 리뷰를 남기고, 병합 조건의 리뷰로 친다. `review --spec` 은 명세 리뷰어도 본 리뷰이고, `--spec` 도 `--minor` 도 없는 리뷰는 명세 리뷰어를 띄우지 않은 이유를 요약에 적어야 남는다. `review` 는 앞 리뷰보다 남은 막는 지적이 줄었는데 그 사이 slip 도 새 red 도 없으면 받지 않는다. 오탐이나 결정과 어긋나 고치지 않고 뺀 수는 `--dropped=<수>` 로 받는다. 옵션은 다른 인자의 앞뒤 어디에 써도 읽고(뒤의 인자를 모두 경로로 받는 `--paths` 는 맨 끝에 쓴다), 모르는 옵션은 어느 명령에서든 받지 않는다. `--` 로 시작하는 한 단어를 제목이나 이유 같은 값으로 넣으려면 그 앞에 `--` 를 따로 둔다. 되돌릴 수 있는가(`door`)를 남겨야 병합되고, 한쪽 문(되돌릴 수 없음)이면 병합은 사용자가 정한다. 기록 명령은 무엇을 기록했는지 한두 줄만 찍고(`log` 는 명령이 실패했을 때만, `red` 는 늘 실패 출력의 끝을 붙인다), 답을 받지 못한 질문이 있으면 그 사실을 한 줄 덧붙인다. 기록 전체는 `show`, 병합 전에 빠진 것은 `check` 에서만 나온다. `show` 의 첫 줄은 상태이고, 기본 출력은 완료 기준마다 한 줄이다. 명령 전문과 로그는 `show --full` 에서 나오고, `show --save` 는 그 전문을 메인 체크아웃의 git 폴더 안 파일에 써서 워크트리가 지워져도 남긴다. 기록은 워크트리의 git 폴더 안에 있어 커밋되지 않는다. `ask` 는 사용자에게 물은 것을 남기고 `answered` 는 받은 답을 적는다. 답이 없는 질문은 `show` 의 상태 줄 바로 아래에 번호째 나온다.
- `hooks/merge_gate.py`: base 로 들어가는 병합 직전에 그 작업 워크트리의 `job` 기록을 본다. `gh pr merge` 는 CI 와 PR 의 최신 커밋이 검증한 로컬 HEAD 와 같은지도 본다. PR 없이 base 를 체크아웃한 곳에서 작업 브랜치를 합치는 `git merge` 와 작업 브랜치를 base 로 보내는 `git push` 도 본다(작업 브랜치에서 base 를 합치는 `git merge` 는 보지 않는다). 기록은 세션의 현재 폴더만이 아니라 명령이 가리키는 폴더(`cd`, `git -C`)와 병합하는 브랜치(`gh pr merge` 는 PR 의 브랜치)가 체크아웃된 워크트리에서 찾는다. 빠진 것이 있거나 「PR 까지만」인 작업이면 병합을 막고 이유를 알리며, 실수 기록에 남긴다. `job` 기록이 없는 곳에서는 아무것도 하지 않는다. 실수를 막는 난간이지 보안 경계가 아니다.
- `hooks/review_gate.py`: `job.py review` 직전에 버그 축 리뷰(`code-review`)가 실제로 diff 를 읽었는지 세션 기록에서 본다. 「읽었다」는 도구 이름이 아니라 내용으로 본다. 받은 앞 리뷰 뒤에 code-review 의 지시문이 나온 기록 파일에서, 그 뒤에 받은 도구 출력(cat, Read, `git diff`, 나눠 읽기 어느 것이든)에 `bug.patch` 의 줄이 모두 들어 있어야 받는다. 잘린 출력은 앞부분만 읽은 것으로 치고, 막을 때 보이지 않은 줄 범위를 알린다. 명세 리뷰어가 읽은 것은 치지 않는다. 판정할 수 없으면(세션 기록 없음, `bug.patch` 없음, 레포가 OS 임시 폴더 아래, 훅이 죽음) 막지 않되 그 이유를 에이전트와 사용자에게 알린다. 막으면 실수 기록에 남긴다.
- `hooks/permission_gate.py`: 사람 없는 `job`(`job.py start --unattended`)에서 승인 창이 뜨려 하면 기다리지 않고 거부한다. 막힌 일이 완료 기준에 꼭 필요하면 작업은 막힌 자리를 보고하고 끝나고, 곁가지면 그 일을 빼고 이어 간다. 거부하면 실수 기록에 남긴다. 기록은 세션의 현재 폴더, 명령이 가리키는 폴더(`cd`, `git -C`), 파일 도구가 고치는 파일의 폴더에서 찾는다. 그 밖의 세션에서는 아무것도 하지 않는다.
- `hooks/destructive_gate.py`: **fade 를 깐 모든 세션의 Bash 호출에 걸린다.** `job` 과 상관없이 세션의 동작을 바꾸는 fade 의 유일한 훅이다. 루트, 홈과 그 위 폴더, `~/.ssh` 의 재귀 삭제, 기본 브랜치(main, master, 그 레포의 기본 브랜치)로의 force push, 장치에 쓰는 `dd`, `mkfs` 를 거부한다. 인용된 글자와 heredoc 본문은 명령으로 치지 않는다. 막기만 하고 허용은 하지 않으며, 꼭 필요한 명령은 사용자가 터미널에서 직접 친다. 끄려면 fade 플러그인을 끈다.
- 실수 기록 `~/.claude/fade/mistakes.jsonl`: 레포와 작업을 넘어 모이는 실수가 한 줄에 하나씩 쌓인다. 병합 훅과 승인 창 훅이 막을 때, `job.py stop`, `job.py slip`(리뷰에서 고친 막는 지적, CI 실패, 써 보기에서 찾은 버그, 사용자 지적)이 쓴다. `slip` 은 같은 실수끼리 묶는 이름(key)을 받아 함께 적고, 훅과 `stop` 이 쓴 줄의 key 와 처리는 `hardener` 가 적는다. PR 을 열기 전에 찍힌 줄의 PR 칸은 `job.py pr` 이 채운다. 환경 변수 `FADE_MISTAKES` 로 경로를 바꾼다. 레포가 OS 임시 폴더 아래(테스트, 써 보기)에 있으면 `FADE_MISTAKES` 를 정하지 않은 동안 쓰지 않는다. 공개 PR 에 붙는 `show` 의 출력은 홈 경로와 Claude 가 경로로 만든 폴더 이름(`-Users-<이름>-`) 속 사용자 이름을 가린다.
- `tests/`: 위의 스크립트와 훅, 에이전트 정의, `nonstop.py` 의 테스트. PR 마다 GitHub Actions 로 돈다.

## 설치

```bash
claude plugin marketplace add Hwan3434/fade
```

```bash
claude plugin install fade@fade
```

데스크톱 앱은 같은 설정을 읽으므로 CLI 로 한 번 설치하면 둘 다에서 쓴다. Claude 클라우드 세션은 플러그인을 읽지 않는다. 클라우드에서 쓸 레포에는 스킬 폴더 사본을 `.claude/skills/` 에 넣는다. 사본에는 `bin/` 이 없으니 `job.py` 는 스킬 글이 적은 다른 모양(`python3 "${CLAUDE_SKILL_DIR}/job.py"`)으로 불린다. claude.ai 와 Cowork 는 최상위에 `bin/` 이 있는 플러그인을 설치하지 않으므로 fade 도 그곳에는 설치되지 않는다.

## 참고한 곳

- [mattpocock/skills](https://github.com/mattpocock/skills): `grill` 은 `grilling`, `debug` 는 `diagnosing-bugs` 에서 출발했다. `code-review` 의 명세 축은 `reviewer` 의 명세 충족으로, `tdd` 의 테스트 기준(기대값은 독립된 상수, 자기 모듈은 목으로 바꾸지 않는다)은 `reviewer` 의 테스트 품질로, `retro` 는 `hardener` 로, `pr` 의 Merge Danger(한쪽 문·양쪽 문, 영향 범위)는 `job.py door` 로 들여왔다.
- [obra/superpowers](https://github.com/obra/superpowers): `subagent-driven-development` 의 리뷰어(구현자의 보고를 믿지 않고 diff 로 확인)는 `reviewer` 로, `brainstorming` 의 builder check 는 `dispatch` 의 계획서 빈칸 검사로 들여왔다.
- [garrytan/gstack](https://github.com/garrytan/gstack): `careful` 은 파괴적 명령 차단 훅으로, `qa-only` 는 `tester` 로, `land-and-deploy` 의 PR 커밋 대조는 병합 훅으로 들여왔다.
- [cursor/plugins](https://github.com/cursor/plugins) 의 `pstack`: 검사를 싣지 않는 방식.
- [poteto/verification-skill-example](https://github.com/poteto/verification-skill-example): 검증 스킬의 본보기.
