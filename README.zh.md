# fade

[한국어](README.md) · [English](README.en.md) · [日本語](README.ja.md)

只面向 Claude Code 的技能插件，在 Claude 桌面应用（Code 标签页）和 Claude CLI 中使用。使用其他代理（agent）的人，可以读一读技能，按自己的环境改写。它不是为了增加功能而做的，而是为了不断变少而做的。
目标是模型越聪明，就删掉越多的文字，最终归零，所以叫 fade。变少的是文字；守护流程的结构（脚本、钩子、测试）会留下来。

## 为什么做它

### 终极目标

> 归根结底，我希望有一天不再需要这个技能。做减法的目的本身，就是盼着 AI 聪明到无需多加解释的那一天；在 AI 已经变聪明的前提下，我们在践行做减法的美学。

### 信任 AI 意味着什么

> 信任 AI 意味着什么，每天都在变，每出一个新模型就变一次。但信任 AI 是指尽量少向 AI 解释，而不是不做静态检查、钩子、lint 和测试。这些是必需的；在它们之上，无论智能体前进还是后退、右转还是左转，我们都信任它。

### 这个工具的位置

> 做不好的东西就不要替人去做，让开发者自己做。我们是在开发者做好的东西之上控制 AI 的工具，不介入静态检查这一层。

### 放弃的路

> 想用文字去控制智能体。核心就是这一点。

## 怎么做的

- 守护仓库的工作（静态检查、hook、lint、测试、验证手段）由那个仓库负责。fade 只承载在其之上主控（lead）和工作者（worker）的工作方式。
- 这种工作方式也尽量用结构而不是文字来守。`job` 的阶段记录由脚本（`job.py`）保存，它只记录自己亲自运行测试命令确认过的结果；合并之前，钩子会检查这份记录和 CI。fade 附带的结构只有与具体仓库无关的、fade 自己的工作形式，以及一个在所有会话里拦下几种不可逆命令的钩子。
- 即便是能用文字约束的规则，只要能用检查拦住，就从技能里拿掉，交给检查。首先交给那个仓库的检查；因人而异的东西交给那个人自己的设置。技能里只留下流程。
- 所以它只在检查齐全的仓库里才能好好运转。无人值守运行的 `nonstop` 只靠拒绝仓库要求确认的操作来停下；在没有这些检查的仓库里，没有任何东西能拦住那些操作。
- 因仓库、因人而异的值（base 分支、合并方式、分支名、验证方法）不写进来。由那个仓库的规则和那个人的设置决定，模型读取并遵循它们。
- 只有在真实会话中确认出现了某一行要防止的失败，才会加上那一行。描述模型本来就会做的事的行则删掉。
- 只收录在多个仓库中以同样正文使用的内容。不规定在哪个应用里运行。只写要满足的条件，满足条件的方法由模型从该环境提供的方式中选择。

## 往哪里去

- 每出一个新模型，就试着逐行删除。如果模型没有那一行也能做好，那一行就不会再回来。
- 只有确认出现失败时才会加行。加上的行也终究是将来要删的候选。
- 不再使用的结构也会删掉。但不会仅仅因为模型变好了就删掉检查。
- 当技能一个个消失、最后一行也被删掉时，就是这个插件完成的时候。

## 技能

- `job`：工作的最小单位。接收一份计划书，先写测试，再实现、留证据、亲手试用，反复做代码审查直到没有阻断性意见，再提 PR、合并、报告。审查总是跑 bug 轴；是否加跑规格轴不按行数这类固定标准，而由审查的一方看变更的性质（是否涉及多条完成标准、是改行为还是只改文字、是否触及合并条件或钩子这类出错也不报错的地方、能否一遍读完）自行判断。决定不跑时，把理由记进审查记录。bug 轴把 `job.py review-files` 写出的 `bug.patch`（第一次审查是连测试和文字在内与 base 的全部差异，再次审查是已接受的上一次审查之后的部分）读到最后。每条意见都要对照计划书：要推翻计划书已定之事的意见不改，记为“与决定冲突”；如果看起来是那个决定本身错了，就列进报告的“需要决定的事”。修正之后只重新审查修正的部分，也只重做依赖于被改路径的证据和试用。审查进行期间只修正阻断性意见；次要意见先记下，等阻断性意见清零后合并到一个提交里一次修完，然后只对这个提交跑 bug 轴。审查者、测试者这类代理的回答要在不结束回合的情况下等待。遇到解决不了的问题或需要用户决定时，就在那里停下并报告。用户若缩小范围（比如“只到 PR”），就只做到那一步。报告里不再重抄完整记录，第一行写贴在 PR 上的记录评论的地址（没有 PR 或评论失败时写记录文件的路径）。问过用户的问题会记下来，还没得到回答的问题紧接在这个地址之后按编号重新写出。PR 正文是给人读的摘要（结果、能否撤回、所做选择中重要的部分及理由、没能修好的部分、每条完成标准一行），不贴完整记录。提交不是在最后一次性做，而是按失败的测试、实现、修正阻断性意见这类意义不同的步骤分开，提交信息写明改了什么、为什么改。
- `try`：启动 `tester` 代理，按用户实际使用的方式试用成果，并按每种情况留下画面和日志。
- `harden`：不往指示里加文字，而是用检查（lint、测试、钩子、权限设置）拦住 AI 犯过的错。
- `grill`：在执行前把剩下的决定逐一追问到底，每个问题都带编号和推荐答案。
- `dispatch`：把代码改动以 `job` 计划书的形式交给在仓库 worktree 中运行的新会话（工作者），并将工作者留在 PR 或记录文件里的证据与完成标准对照。用当前环境提供的、能满足全部条件（自己的 worktree、相同环境、无人值守跑完、能知道结束、能对话、能接手）的方法启动工作者；没有能满足的方法就不启动，并说明缺什么。不用关闭权限检查的方式启动；启动结果不明确时，再次启动前先确认实际生成了什么。工作者的模型取用户这次说的值，没有就取用户指示文件里的值，定好再启动；两者都没有时，启动前告知用户工作者会沿用主控的模型。启动前先让一个新的子代理找出计划书的空缺；工作者结束后，把 `hardener` 的检查建议转告用户。PR 合并或关闭后，不再询问，直接清理工作者的 worktree、已合并的工作分支和工作者会话（有未提交的改动或远端没有的提交时不删除）。不给仍在运行的工作者发送追加标准的消息，因为那样会丢失该工作者上一轮报告的通知。如果还是发了，就找到它上一轮报告的全文转告用户。
- `debug`：先做出一条会失败的命令，再按固定顺序诊断 bug。
- `nonstop`：无人值守地把任务列表跑到底，每个任务都以 `job` 执行。只在用户亲自调用时使用。每当一个任务合并后，按与 `dispatch` 清理相同的检查，删除该任务的 worktree 和分支。只到 PR 的任务以及搁置或受阻的任务保留不动。

## 代理

由技能启动的子代理，定义在 `agents/` 里。不指定模型，按使用者选择的模型运行。

- `reviewer`：`job` 的规格轴审查者。不相信实现者的报告，把计划书和 diff 逐条对照，先看是否满足规格（遗漏、多做、理解错），再看测试质量。每条意见都标明是阻断性意见还是次要意见。工具只有读取（Read、Grep、Glob）。
- `tester`：像用户一样试用成果，只做报告。先写场景，画面和输出留在 worktree 的 git 目录中的 `fade-try/` 里。仓库外临时文件夹里的文件可能被删掉，`job.py` 不把它们收作证据。去掉了编辑工具（Edit、Write、NotebookEdit）。
- `hardener`：把已完成工作的失误在失误记录里按 key 归类；同一个 key 出现两次以上，或是谁都可能犯的失误，就按 `harden` 的顺序提出检查建议。只提建议，不动手修改。

## 结构

- `bin/`：插件启用期间，Claude Code 会把这个文件夹放进 Bash 工具的 PATH。里面是让 `job.py` 和 `nonstop.py` 不带路径就能调用的入口，本体在 `skills/` 下。
- `skills/job/job.py`：`job` 的阶段记录。实现前的失败（red）和实现后的通过（green）只有在亲自运行命令确认后才会记录；red 会打印失败输出的末尾，green 如果发现 red 之后没有任何文件的内容变了（实现早在 red 之前就有了，或者是仓库外的变化让它通过），就不予记录；实现在 red 之前就已提交、或只改测试让它通过的情况无法分辨，因为哪些文件是测试因仓库而异；证据和亲手试用只有附上文件才会记录。合并条件中的 green 和审查只认在当前提交上取得的。证据和试用如果写明了所依赖的路径（`--paths`），只要这些路径在取得它的提交之后没有变化就一直有效；没有写路径的只认在当前提交上取得的。`review-files` 会报告判断是否启动规格审查者的材料：与 base 的 diff 行数、改动文件的数量和列表，从第二次审查起，只把规格审查者最后看过的提交之后修正的部分写进给审查者的文件。base 的 `.gitattributes` 里标为 `linguist-generated`、`-diff`、`binary` 的文件（生成文件、锁文件）会从审查用的 diff 中去掉，其名称和行数留在输出和 `show` 里。本分支新加的标记要等合并之后的工作才生效（免得分支自己把自己的文件去掉）。读取 base 的标记需要 git 2.40 或更新，用 base 的标记生成 diff 需要 2.42 或更新；更旧时分别什么都不去掉，或用工作区的标记生成并提示。fade 不持有文件名或扩展名列表，仓库没有标记就不去掉。`bug.patch` 超过 20000 个字符时，还会把按文件边界切开的片段写到 `.fade-review/parts/`，以便每个片段各调用一次 code-review。`review --minor` 记录对「集中修正次要意见的那一个提交」所做的 bug 轴审查，并算作合并条件里的审查。`review --spec` 表示规格审查者也看过的审查；既没有 `--spec` 也没有 `--minor` 的审查，必须在摘要里写明没有启动规格审查者的理由才会记录。`review` 在剩余阻断性意见比上一次少、而其间既没有 slip 也没有新的 red 时不予记录；以误报或与决定冲突为由不改而扣掉的数量用 `--dropped=<数>` 给出。选项写在其他参数前后都能识别（`--paths` 会把后面的参数全部当作路径，所以放在最后），不认识的选项在任何命令里都不接受。要把以 `--` 开头的单个词作为标题或理由这类值传入，就在它前面单独放一个 `--`。必须记下能否撤回（`door`）才能合并；如果是单向门（无法撤回），由用户决定是否合并。记录命令只输出一两行，说明记了什么（`log` 只有在命令失败时才附上输出末尾，`red` 总是附上失败输出的末尾）；还有没回答的问题时再加一行提示。完整记录只由 `show` 给出，合并前还缺什么只由 `check` 给出。`show` 的第一行是状态，默认输出是每条完成标准一行。完整命令和日志在 `show --full` 中给出，`show --save` 把这份全文写进主检出的 git 文件夹里的文件，worktree 删掉后也还在。记录放在 worktree 的 git 目录里，不会被提交。`human-done` 在人确认之后解除需要人看的项，并记下谁依据什么解除的。`contrasted` 和 `hardened` 记下主控把工作者的记录与完成标准对照的结果和 hardener 的结果。`resume` 在人确认之后解除停下的作业（`stop`）。`log` 和 `red` 不接受含管道（`|`）的命令、仓库外操作系统临时文件夹里的脚本、以及调用只该由主控记录的命令。记录在重读、修改、保存之间加锁，同时运行几个也不会丢。`ask` 记录问过用户的问题，`answered` 记录得到的回答。没有回答的问题会按编号出现在 `show` 的状态行正下方。
- `hooks/merge_gate.py`：在合并进 base 之前检查该工作 worktree 的 `job` 记录。对 `gh pr merge` 还检查 CI，以及 PR 的最新提交是否就是验证过的本地 HEAD。不走 PR 时，在检出 base 的地方合入工作分支的 `git merge`、把工作分支推到 base 的 `git push` 也会检查（在工作分支上合入 base 的 `git merge` 不检查）。记录不只在会话的当前文件夹里找，也在命令指向的文件夹（`cd`、`git -C`）和检出被合并分支（`gh pr merge` 时为 PR 的分支）的 worktree 里找。若有缺漏，或这次工作“只到 PR”，就拦下合并、说明原因，并写进失误记录。没有 `job` 记录的地方什么也不做。它是防止失误的护栏，不是安全边界。
- `hooks/review_gate.py`：在 `job.py review` 之前，从会话记录里检查 bug 轴审查（`code-review`）是否真的读了 diff。“读了”看内容而不看工具名：在已接受的上一次审查之后出现 code-review 指令的那些记录文件里，其后收到的工具输出（cat、Read、`git diff`、分段读取都行，退出码非 0 的输出也算）必须合起来包含 `bug.patch` 的全部行，才予接受。每个输出都按行的位置与 `bug.patch` 对齐（Read 按行号），只算对上的位置，所以同一段开头读两遍也不算读了后面。以错误结束的 code-review 调用不算调用过。在同一个提交上重新记录审查时，按上一次审查看过的范围判定。把大的 diff 按片段分多次用 code-review 审查，也看其总和。被截断的输出只算读了显示出来的部分，拦下时会说明没有出现过的行范围、所在文件以及接着要读的对象。规格审查者或主会话在 code-review 之外读的不算（桌面应用里指令留在主会话记录中，之后主会话收到的输出会算）。只改了带标记的文件、`bug.patch` 为空时予以接受。无法判定时（没有会话记录、没有 `bug.patch`、调用了 code-review 却找不到指令标题、仓库位于操作系统临时文件夹下、钩子出错）不拦，但会把原因告诉代理和用户。对 `job.py review` 以外的命令什么都不输出。拦下时写进失误记录。
- `hooks/permission_gate.py`：在无人值守的 `job`（`job.py start --unattended`）里，权限确认框将要弹出时不等待，直接拒绝。被拦下的操作如果是完成标准所必需的，工作会报告卡住的地方后结束；如果只是旁支，就去掉这一步继续做。每次拒绝都会写进失误记录。记录在会话的当前文件夹、命令指向的文件夹（`cd`、`git -C`）和文件工具所改文件的文件夹里找。其他会话里什么也不做。
- `hooks/destructive_gate.py`：**作用于所有安装了 fade 的会话中的每一次 Bash 调用。** 这是 fade 里唯一与 `job` 无关、会改变会话行为的钩子。它拒绝递归删除根目录、主目录及其上层目录、`~/.ssh`，拒绝向默认分支（main、master 或该仓库的默认分支）force push，拒绝向设备写入的 `dd` 和 `mkfs`。解读命令的方式和合并钩子相同（被引号括起的文字和 heredoc 正文不当作命令，去掉重定向，跟随同一行里的 `cd`）。在无法确定文件夹的 `cd`（shell 变量、命令替换、用 `&&` 以外方式连接的不存在的文件夹）之后，删除那个文件夹本身或更上层的相对路径（`.`、`*`、`..`）也会拒绝。它只拒绝、不放行；真正需要的命令由用户在终端里亲自输入。想关掉它就停用 fade 插件。
- `hooks/lead_gate.py`：不让运行 `job` 的会话自己去做只有人和主控才做的事。由 dispatch 启动的工作者（即使有人在），以及会话记录里清楚显示在该 worktree 中运行过 `job.py start` 的无人值守作业的会话（包括子代理），不能记录该作业的 `job.py human-done`、`contrasted`、`hardened`、`resume`。直接调用和用 `log`、`red` 包起来的调用会被拦住，`bash -c`、`eval`、放在 shell 变量里的调用拦不住。已合并的工作者的 worktree，在主控的 `contrasted` 和 `hardened` 记录齐全之前，不能用 `git worktree remove` 或整个文件夹的 `rm -r` 删除。当前会话自己开始的作业的清理（`nonstop`）不拦，但用 dispatch 的第一条指令开始的工作者即使有人在也需要主控的记录。未合并的作业、没有 `job` 记录的 worktree 都不拦。谁开始的作业，靠在会话记录里找该 worktree 中运行的 `job.py start` 来区分；无法确定文件夹的 `start`（通过 shell 变量 cd 的）不算，不做猜测；没有会话记录就不拦。环境在关闭会话时连 worktree 一起删除，那不经过 Bash，这个钩子拦不住。
- 失误记录 `~/.claude/fade/mistakes.jsonl`：跨仓库、跨工作汇集的失误，一行一条。合并钩子和权限确认钩子拦下时、`job.py stop`、`job.py slip`（审查中修好的阻断性意见、CI 失败、试用时发现的 bug、用户指出的失误）都会写入。`slip` 接收把同一种失误归为一组的名字（key）并一起写入，钩子和 `stop` 写的行的 key 和处理情况由 `hardener` 填写。PR 打开之前记下的行的 PR 栏由 `job.py pr` 补上。可以用环境变量 `FADE_MISTAKES` 改路径。仓库位于操作系统临时文件夹下（测试、试用）时，只要没设 `FADE_MISTAKES` 就不写入。给为试用而启动的会话设 `FADE_TRY_REPO=<要试用的仓库>`，该会话的 `job.py` 就不会碰那个仓库以外的作业记录，也不会写入默认的失误记录。贴到公开 PR 上的 `show` 输出会隐去主目录路径和 Claude 由路径生成的文件夹名（`-Users-<名字>-`）中的用户名。
- `tests/`：上面的脚本和钩子、代理定义以及 `nonstop.py` 的测试，每个 PR 都由 GitHub Actions 运行。

```bash
claude plugin install fade@fade
```

桌面应用读取同样的设置，所以用 CLI 安装一次，两边都能用。Claude 云端会话不会读取插件。要在云端使用的仓库，把技能文件夹的副本放进 `.claude/skills/`。副本里没有 `bin/`，所以 `job.py` 按技能文字给出的另一种写法（`python3 "${CLAUDE_SKILL_DIR}/job.py"`）调用。claude.ai 和 Cowork 不安装顶层带 `bin/` 的插件，所以 fade 也装不到那里。

fade 在 macOS 和 Linux 上运行。`job.py` 和钩子用 `fcntl` 加文件锁，所以在 Windows 上钩子会以错误结束、什么也拦不住，`job.py` 也无法运行。

## 参考

- [mattpocock/skills](https://github.com/mattpocock/skills)：`grill` 源自 `grilling`，`debug` 源自 `diagnosing-bugs`。`code-review` 的规格轴成了 `reviewer` 的规格检查，`tdd` 的测试准则（预期值用独立常量，不 mock 自己的模块）成了 `reviewer` 的测试质量检查，`retro` 成了 `hardener`，`pr` 的 Merge Danger（单向门还是双向门、影响范围）成了 `job.py door`。
- [obra/superpowers](https://github.com/obra/superpowers)：`subagent-driven-development` 里的审查者（不相信实现者的报告，用 diff 核实）成了 `reviewer`，`brainstorming` 的 builder check 成了 `dispatch` 的计划书空缺检查。
- [garrytan/gstack](https://github.com/garrytan/gstack)：`careful` 成了拦截破坏性命令的钩子，`qa-only` 成了 `tester`，`land-and-deploy` 的 PR 提交核对成了合并钩子的一部分。
- [cursor/plugins](https://github.com/cursor/plugins) 中的 `pstack`：不附带检查的方式。
- [poteto/verification-skill-example](https://github.com/poteto/verification-skill-example)：验证技能的范例。
