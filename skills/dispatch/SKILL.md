# dispatch — 워커에 작업 맡기기

| 용어 | 뜻 |
|---|---|
| 세션 | Claude 와의 대화 하나. 자기 폴더·기록·권한 설정을 가진다 |
| 리드 | 이 스킬을 부른 세션. 어느 레포에서 열었든, 여러 레포를 모아 둔 상위 폴더에서 열었든 같다. 워커를 띄우고, 보고를 옮기고, 증거를 완료 기준과 대조한다 |
| 워커 | 리드가 이 스킬로 띄운 세션. 목표가 걸린 레포의 자기 워크트리에서 작업 하나를 하고 병합(사용자가 줄였으면 PR)으로 끝낸다. GitHub 원격이 없는 폴더면 그 폴더에서 하고 PR 없이 끝낸다. 사용자가 열어 말을 걸 수 있다 |

리드는 워커를 띄운 뒤 구현에서 손을 뗀다.

- 호출됐다는 것이 맡기기로 한 결정이다. 결과물이 코드 변경이 아니면(답만 필요한 조사) 여기서 직접 한다.
- 계획서는 워커의 첫 지시문에, 결과는 PR 에 남는다. 요약은 본문에, 기록 전문은 기록 댓글에 있다.

## 1. 계획서

워커마다 `job` 스킬의 계획서를 쓴다. 칸과 쓰는 법은 이 스킬 폴더 옆 `job/SKILL.md` 의 「계획서」 절을 읽는다. 리드는 `job` 스킬을 직접 실행하지 않는다. 사용자는 워커가 뜨면 자리를 떠나니 띄우기 전에 채운다.

- 요청이 여러 레포에 걸치면 관련 레포의 코드를 읽어 구현할 수 있는지만 판정하고, 레포별 목표로 나눈다. 한 워커의 계획서에는 그 레포의 목표만 담는다. 상세 계획, 설계, 레포 사이의 API 는 리드가 정하지 않는다. 워커가 자기 레포에서 정한다.
- 사용자가 범위를 줄였으면(「PR 까지만」) 그 말을 「특이사항」에 그대로 넣는다.

### 계획서 빈칸 검사

띄우기 전에 새 서브에이전트(이 대화를 물려받지 않는 것)에 계획서만 주고, 이것만으로 만들려면 물어야 할 것을 뽑게 한다. 워커처럼 그 레포를 읽는 것은 된다. 이 답이 있어야 워커를 띄우니 백그라운드로 띄우지 않고, 답이 올 때까지 기다리는 방식으로 띄운다. 워커가 여럿이면 계획서마다 하나씩 한 메시지에서 함께 띄우고 함께 기다린다. 나온 질문을 셋으로 나눈다.

- 이미 답 있음: 계획서나 레포에 답이 있다. 그대로 둔다.
- 사소함: 리드가 정해 계획서에 적는다.
- 사용자 결정 필요: 사용자에게 한 번에 묻고, 답을 계획서에 적는다.

## 2. 워커 띄우기

지금 있는 환경이 주는 방법 가운데 아래 조건을 모두 채우는 것으로 워커를 띄운다. 어떤 방법이 있는지는 그 환경의 안내(도구 설명, 설치된 스킬, 명령의 도움말)를 읽고 리드가 판단한다. 조건을 채울 방법이 없으면 띄우지 않고 무엇이 없는지 사용자에게 알린다.

| 조건 | 뜻 |
|---|---|
| 자기 워크트리 | 목표가 걸린 레포의 base(그 레포의 규칙에서 읽는다)에서 딴 새 브랜치와 워크트리에서 돈다. GitHub 원격이 없는 폴더면 그 폴더에서 돌고, 같은 폴더에는 워커를 하나만 둔다 |
| 같은 환경 | 사용자의 메모리, 지침 파일, 설정을 리드와 똑같이 읽는다 |
| 사람 없이 끝까지 | 지켜보는 사람이 없어도 권한 확인에서 멈추지 않는다 |
| 끝을 안다 | 워커가 턴을 끝내면 리드가 알고, 보고 전문을 읽을 수 있다 |
| 말을 건다 | 리드가 도는 중에도, 끝난 뒤에도 워커에 이어 말할 수 있다 |
| 넘겨받는다 | 사용자가 워커 대화를 열어 직접 말을 걸 수 있다 |

먼저 같은 작업이 이미 떠 있는지 본다.

- 레포가 그 환경에 등록돼 있어야 띄울 수 있으면 등록부터 하고, 등록한 것을 사용자에게 알린다.
- 권한 검사를 끄는 방식으로는 띄우지 않는다. 환경의 기본값이 그렇게 띄우게 돼 있으면 띄우지 않고 사용자에게 알린다. 「사람 없이 끝까지」는 승인이 필요한 일을 거부하고 막힌 일로 보고하게 해서 채운다.
- 띄운 결과가 모호하면(성공인지 알 수 없는 오류, 응답 없음) 다시 띄우기 전에 실제로 무엇이 생겼는지(워크트리, 브랜치, 세션)를 확인한다. 확인 없이 다시 띄우지 않는다. 같은 작업의 워커가 둘이 된다.
- 리드가 워커의 끝을 스스로 알 수 없으면(워커가 끝나도 리드가 스스로 깨어날 수 없으면) 그 사실과, 사용자가 무엇을 해 주면 되는지를 띄운 직후에 알린다.

워커 모델을 정해서 띄운다. 사용자가 이번에 말한 값을 쓰고, 없으면 사용자 지침 파일에 적힌 값을 쓴다. 둘 다 없으면 워커가 리드의 모델을 물려받는다는 것을 띄우기 전에 사용자에게 한 줄로 알린다. 모델 이름은 사람마다 다른 값이라 이 스킬에 적지 않는다.

첫 지시문은 아래뿐이다. 슬래시 명령(`/스킬`)은 받는 쪽에서 펼쳐지지 않을 수 있으니 글로 시킨다.

```markdown
fade:job 스킬로 아래 계획서를 수행한다. 사용자: 없음

<계획서>
```

띄운 뒤 사용자에게 워커를 넘겨받는 방법(그 세션을 여는 길)을 알리고 턴을 끝낸다. 턴을 끝내고 기다리는 것은 워커(세션)뿐이다. 서브에이전트(계획서 빈칸 검사, `fade:hardener`)는 답을 받아야 다음 일을 하니, 「답을 기다립니다」만 남기고 턴을 끝내지 않는다.

- 한 대화를 두 곳에서 동시에 잇지 않는다. 기록이 섞인다.
- 도는 중인 워커에 기준을 더하는 메시지를 보내지 않는다. 보내면 워커의 다음 턴이 바로 시작돼, 리드가 앞 턴의 보고 알림을 받지 못한다. 더할 것은 워커가 턴을 끝낸 뒤에 보내거나 다음 작업으로 미룬다.
- 그래도 도는 워커에 말을 걸었으면, 그 워커의 직전 보고 전문을 찾아 읽고 사용자에게 옮긴 뒤에 다음으로 간다.

## 3. 워커가 턴을 끝내면

보고 전문을 읽고, 그 응답에서 바로 사용자에게 옮긴다. 알림에 보고 일부만 오면 전문을 찾아 읽는다.

- 결정할 것을 앞에 두고, 워커가 사용자에게 묻는 것(선택지, 확인 요청)은 번호째 전부 옮긴다.
- 워커의 질문에 답하기 전에 사용자가 워커 대화에서 이미 답했는지 본다.
- 계획서와 이 대화에 근거가 있는 질문은 리드가 워커에 답하고 사용자에게 한 줄로 알린다. 새 판단이 필요하면 워커가 쓴 근거째 사용자에게 옮긴다.
- 리드에서 막힌 일은 워커가 아니라 사용자에게 돌린다.

## 4. 완료 판단

워커의 기록 전문(`job.py show --full`: 실행한 명령과 출력, 화면 캡처의 절대 경로, 로그)을 읽어 완료 기준과 하나씩 대조한다. 워커의 보고에는 전문이 없고 남긴 곳만 적혀 있다. 보고가 가리키는 곳을 읽는다. PR 의 기록 댓글(`gh pr view <번호> --comments` 의 마지막 기록)이거나, PR 이 없거나 댓글이 실패하면 보고가 적은 기록 파일(`job.py show --save` 가 쓴 것)이다. 워커는 기본으로 병합까지 하므로 이 대조는 병합 뒤에 하는 두 번째 확인이다. 증거가 없거나 기준과 맞지 않으면 사용자에게 보고하고, 이미 병합됐으면 되돌릴지(revert) 묻는다. `gh pr diff` 는 사용자가 묻거나 반문할 때만 본다. CI 결과도 읽는다.

증거를 낼 수단이 그 레포에 없으면 「이 레포에는 증명할 수단이 없다」고 사용자에게 보고만 하고, 수단을 만들지 않는다.

워커 보고를 받은 뒤 `fade:hardener` 에이전트를 띄워(워커의 워크트리 경로, PR 주소, PR 이 없거나 기록 댓글이 실패했으면 기록 파일의 경로를 준다) 제안을 사용자에게 옮긴다. hardener 도 백그라운드로 띄우지 않고 답이 올 때까지 기다리며, 워커 여럿의 보고가 함께 왔으면 한 메시지에서 함께 띄운다. 레포의 검사 제안은 사용자가 받아들이면 그 레포의 워커에 `job` 으로 맡기고, 사용자 settings 와 fade 훅은 사용자가 정한다. 정리 대상으로 표시된 실수 기록은 사용자가 지우라고 할 때만 지운다.

### 정리

PR 이 병합되거나 닫히고 위의 대조와 hardener 가 끝나면 묻지 않고 정리한다(hardener 가 그 워크트리에서 `job.py slip` 을 돌린다). PR 까지만인 작업도 그 PR 이 병합되거나 닫힐 때 정리한다. 멈춘 작업(`job.py stop`, `job.py show` 첫 줄이 「상태: 멈춤(…)」)은 정리하지 않는다.

1. **워크트리를 검사한다.** 커밋 안 된 변경이나 추적하지 않는 파일(`git -C <워크트리> status --porcelain` 에 나오는 것)이나 원격에 없는 커밋이 있으면 그 워커는 정리하지 않고 보고한다. 원격에 없는 커밋은 base 가 아니라 병합된 PR 의 head(`gh pr view <번호> --json headRefOid`)나 원격 작업 브랜치와 견준다. squash 병합이면 작업 브랜치의 커밋이 base 의 조상으로 남지 않기 때문이다. 로컬 브랜치가 그 head 와 같거나 그 조상이면 원격에 없는 커밋이 없다. PR 이 없으면(원격이 없어 base 에 바로 반영했으면) 반영한 base 와 견주고, 로컬 브랜치가 base 의 조상이면 남은 커밋이 없다.
2. **세션과 워크트리를 치운다.** 환경이 주는 방법으로 워커 세션을 닫거나 보관한다. 그 방법이 워크트리까지 지우는지 먼저 확인하고, 지운다면 1번을 먼저 끝낸다. 지우지 않으면 세션을 닫은 뒤 `git worktree remove <워크트리>` 로 워크트리를 지운다(워크트리가 레포 밖에 있어도 같다). 닫기가 거부되면 다시 시도하지 않고 남은 세션을 보고에 적고, 그 워커의 로컬 브랜치는 워크트리에 체크아웃된 채라 3번에서 지우지 않는다. 세션을 닫을 방법이 환경에 없으면 세션은 두고 워크트리만 지운다.
3. **브랜치를 지운다.** 병합된 작업 브랜치를 로컬과 원격에서 지운다. 원격에 이미 없으면 건너뛴다. 닫히기만 한 PR 의 브랜치는 남긴다.
