# job — 업무 하나

계획서 하나를 받아 끝까지 수행한다.

## 계획서

넘기는 글은 이 모양이다.

```markdown
fade:job 스킬로 아래 계획서를 수행한다. 사용자: <있음|없음>

# 작업: <제목>
- 목적: <사용자가 원하는 결과>
- 완료 기준: <무엇이 되면 끝인가, 기준마다 보여 줄 증거(테스트·명령 출력, 화면 캡처의 절대 경로, 로그)>
- 사람이 볼 것: <사람이 봐야만 판정되는 것. 없으면 "없음">
- 자료: <내용째. 없으면 "없음">
- 특이사항: <사용자의 말 그대로. 없으면 "없음">
```

계획서를 쓰는 쪽이 지킬 것:

- 완료 기준은 사용자가 주면 그대로 넣고, 주지 않았으면 레포를 읽고 정해 사용자에게 확인받는다.
- 받는 세션은 쓰는 세션의 대화와 메모리를 보지 못한다. 티켓 본문, 계획서, 결정 사항은 내용째 담고, 이미지 같은 자료는 절대 경로를 적는다. 레포와 전역 지침 파일의 내용은 받는 세션도 읽으니 옮겨 적지 않는다.
- 사용자가 범주로 정한 것(「앱바는 전부 56」)은 범주로 적는다.
- 이번 작업에만 걸리는 제약은 사용자의 말 그대로 「특이사항」에 적는다.

## 시작하기 전에

- 「사용자」가 적혀 있지 않으면 있음으로 본다.
- 목적이나 완료 기준이 비어 있으면, 사용자 있음이면 `grill` 스킬로 채운다. 사용자 없음이면 시작하지 않고 빈 칸을 보고한다.
- 사용자 있음이면 평소처럼 사용자와 대화한다. 아래 「사용자 없음일 때」는 적용하지 않는다.

## 사용자 없음일 때

- 목적을 달성할 수 없거나, 목적의 일부를 남기게 되거나, 보안 문제일 때 멈춰서 묻는다. 그 밖의 선택은 스스로 고르고, 무엇을 왜 골랐는지 PR 본문에 적는다. PR 이 없는 작업이면 마지막 보고에 적는다.
- 계획서가 계획의 승인이다. 계획을 보여 주고 답을 기다리지 않는다.
- 계획서에 든 push 와 PR 은 묻지 않고 한다.

## 수행

1. 계획하고 구현한다. 버그 작업이면 `debug` 스킬의 순서를 따른다. 브랜치, 커밋, 테스트, PR 은 그 레포의 규칙대로 한다.
2. 완료 기준마다 증거를 낸다.
3. 커밋하고 PR 을 올린다.
4. 보고한다. 결과와 결정이 필요한 것을 맨 앞에 쓴다(넘긴 세션에는 앞 400자만 간다). 완료 기준마다 원본 증거(실행한 명령과 출력, 화면 캡처의 절대 경로, 로그)를 붙인다.
