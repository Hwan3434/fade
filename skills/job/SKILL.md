# job — 업무 하나

계획서 하나를 받아 끝까지 수행한다. 단계마다 `job.py` 로 기록한다. `job.py` 는 테스트 명령을 직접 돌려 확인한 것만 기록하고, 병합 직전에 fade 훅이 이 기록과 CI 를 본다. 기록이 모자라면 병합이 막힌다.

- `job.py` 는 PATH 에 있는 명령이다. Claude Code 가 플러그인의 `bin/` 을 Bash 도구의 PATH 에 둔다. 경로를 붙이지 않고 `job.py <명령>` 으로 부른다.
- `command -v job.py` 가 아무것도 내지 않으면 `python3 "${CLAUDE_SKILL_DIR}/job.py" <명령>` 을 매번 그대로 쓴다. 긴 경로를 셸 변수에 담아 부르지 않는다. zsh 는 변수에 담은 명령을 낱말로 나누지 않아 명령 이름 하나로 읽고 실패한다.
- 기록 명령은 무엇을 기록했는지 한두 줄만 찍는다(`red` 는 실패 출력의 끝을, `log` 는 실패했을 때 출력의 끝을 더 붙인다). 기록 전체는 `job.py show`, 병합 전에 빠진 것은 `job.py check` 로 본다.

## 계획서

넘기는 글은 이 모양이다.

```markdown
fade:job 스킬로 아래 계획서를 수행한다. 사용자: <있음|없음>

# 작업: <제목>
- 목적: <사용자가 원하는 결과>
- 완료 기준: <무엇이 되면 끝인가. 기준마다 확인할 경우(정상, 경계, 실패, 빈 값 등)와 보여 줄 증거>
- 사람이 볼 것: <사람이 봐야만 판정되는 것. 없으면 "없음">
- 자료: <내용째. 없으면 "없음">
- 특이사항: <사용자의 말 그대로. 범위를 줄였으면(「PR 까지만」) 그 말도. 없으면 "없음">
```

계획서를 쓰는 쪽이 지킬 것:

- 완료 기준은 사용자가 주면 그대로 넣고, 주지 않았으면 레포를 읽고 정해 사용자에게 확인받는다.
- 받는 세션은 쓰는 세션의 대화와 메모리를 보지 못한다. 티켓 본문, 계획서, 결정 사항은 내용째 담고, 이미지 같은 자료는 절대 경로를 적는다. 레포와 전역 지침 파일의 내용은 받는 세션도 읽으니 옮겨 적지 않는다.
- 사용자가 범주로 정한 것(「앱바는 전부 56」)은 범주로 적는다.
- 이번 작업에만 걸리는 제약은 사용자의 말 그대로 「특이사항」에 적는다.

## 시작하기 전에

- 「사용자」가 적혀 있지 않으면 있음으로 본다.
- 레포만의 방식(지침 파일, 설계나 검증 문서, 훅, 승인 규칙)이 이 스킬의 흐름과 다르면 판단해 레포의 방식을 따른다. 그때도 단계 기록은 `job.py` 로 남긴다.
- 목적이나 완료 기준이 비어 있으면, 사용자 있음이면 `grill` 스킬로 채운다. 사용자 없음이면 시작하지 않고 빈 칸을 보고한다.
- 사용자 있음이면 평소처럼 사용자와 대화한다. 아래 「사용자 없음일 때」는 적용하지 않는다.
- 작업할 브랜치와 워크트리에서 `job.py start "<작업 제목>"` 을 돌린다. 사용자 없음이면 `--unattended`, 특이사항이나 사용자가 PR 까지만 하라고 했으면 `--pr-only` 를 붙인다(옵션은 제목 앞뒤 어디에 써도 된다). 사용자가 나중에 범위를 바꾸면 `job.py scope merge|pr` 로 바꾼다.

## 사용자 없음일 때

- 계획서가 계획의 승인이다. 계획을 보여 주고 답을 기다리지 않는다. 선택은 스스로 고르고, 무엇을 왜 골랐는지 커밋 메시지에 적고 중요한 것은 PR 본문에도 적는다. PR 이 없는 작업이면 마지막 보고에 적는다.
- 계획서에 든 push, PR, 병합은 묻지 않고 한다. 승인 창이 뜨려 하면 fade 훅이 대신 거부한다. 레포의 승인 규칙이 그 일에 사람의 확인을 요구하면 레포가 이긴다. 확인해 줄 사람이 없으니 하지 않고 `job.py stop` 으로 멈춰 보고한다.
- 멈추는 때는 아래뿐이다. 이때는 `job.py stop "<이유>"` 로 남기고, 보고하고 끝낸다. 사용자의 답을 기다리는 상태로 끝나는 것이다.
  - 같은 문제를 두 번 고쳐도 남는다(해결하지 못함).
  - 요청대로는 할 수 없어 사용자 결정이 필요하다. 목적을 달성할 수 없거나 목적의 일부를 남기게 되는 때다.
  - 보안 문제다.
  - 권한 설정이나 훅이 막은 명령이 완료 기준을 채우는 데 꼭 필요하다.
- 권한 설정이나 훅이 막은 명령이 완료 기준을 채우는 데 필요하지 않으면(정리, 미리 보기 같은 곁가지) 멈추지 않는다. 그 명령을 빼고 진행하고, 무엇이 막혀 뺐는지 보고에 적는다.
- 어느 쪽이든 막힌 일을 형태만 바꿔 다시 시도하지 않는다.

## 단계

순서대로 한다. 단계에 도착하면 그 단계의 파일(이 스킬 폴더의 `stages/`)을 읽는다.

1. **테스트 먼저**: `stages/test-first.md`
2. **구현**: `stages/build.md`. 버그 작업이면 `debug` 스킬의 순서를 따른다.
3. **증거**: `stages/evidence.md`
4. **직접 써 보기**: `try` 스킬대로 `fade:tester` 에이전트를 띄워 사용자가 쓰는 방식 그대로 써 보게 하고, 턴을 끝내지 않고 보고를 기다려 `job.py tried "<무엇을 어떻게 써 봤나>" <화면·출력 파일>... [--paths <써 본 것이 기대는 경로>...]` 로 기록한다. 써 볼 화면도 명령도 없는 작업이면 `job.py try-na "<이유>"`, 써 볼 것은 있는데 지금 못 하면 `job.py human "<사람이 볼 것>"` 으로 남긴다. `human` 은 써 보기를 대신하지만 남아 있으면 병합하지 않는다.
5. **코드 리뷰**: `stages/review.md`. 남은 막는 지적이 0 이 될 때까지 되풀이한다. 사소한 지적은 그 뒤에 모아 한 커밋으로 고친다.
6. **PR**: `stages/pr.md`
7. **병합**: `stages/merge.md`. PR 까지만인 작업은 건너뛴다.
8. **보고**: 기록 전문(`job.py show --full`)과 원본 증거는 보고에 다시 쓰지 않고, 남겨 둔 곳을 가리킨다. PR 이 있으면 먼저 `job.py show --full | gh pr comment <PR 번호> --body-file -` 로 지금 기록을 PR 에 댓글로 단다. PR 을 연 뒤에 다시 남긴 증거와 병합 기록까지 이 댓글에 든다. PR 이 없거나 댓글이 실패하면(GitHub 의 글자 한도 등) `job.py show --save` 로 기록 전문을 파일에 쓴다. 보고 첫 줄에는 그 댓글의 주소(PR 이 없거나 댓글이 실패했으면 `show --save` 가 찍은 파일의 절대 경로)를 쓴다. 넘긴 세션에는 앞 400자만 가니, 그다음에 답을 받지 못한 질문(`show` 가 상태 줄 바로 아래에 내는 것)을 번호째 다시 적고, 그다음에 결과와 결정이 필요한 것(멈췄으면 멈춘 이유)을 쓴다. 그 아래에 완료 기준마다 결과를 한 줄로 요약한다. 사용자에게 묻는 것은 `job.py ask "<질문>"` 으로 남기고, 답을 받으면 `job.py answered <번호> "<답>"` 으로 적는다.

3·4·5 에서 버그나 막는 지적이 나오면 고치고(테스트를 더했으면 1부터) 3부터 다시 돌되, 고친 범위에 닿는 것만 다시 한다. 고친 커밋이 생기면 green 과 리뷰는 늘 낡은 것이 되고, 증거와 써 보기는 기대는 경로(`--paths`)가 바뀌었거나 경로를 적지 않은 것만 낡은 것이 된다. 리뷰는 고친 부분만 다시 본다. 낡은 것이 남아 있으면 병합 훅이 막고, 무엇이 낡았는지는 `job.py check` 가 알려 준다.

에이전트(tester, reviewer, 그 밖의 서브에이전트)의 답이 다음 단계에 필요하면 백그라운드로 띄우지 않고, 답이 올 때까지 기다리는 방식으로 띄운다. 서로 무관한 에이전트 둘은 한 메시지에서 함께 띄우고 함께 기다린다. 「답을 기다립니다」만 남기고 턴을 끝내지 않는다. 턴을 끝낼 때마다 이 작업을 맡긴 세션이 깨어난다. 도구가 에이전트를 백그라운드로만 띄우면, 답이 오기 전까지 그 답과 무관한 일을 하고, 남은 일이 없으면 기다리는 명령을 돌려 턴을 잇는다.

사용자가 실수를 지적하면 고치기 전에 `job.py slip user <key> "<무엇을 잘못했나>"` 로 실수 기록에 남긴다. key 는 같은 실수끼리 묶는 이름이다. 같은 실수의 key 가 이미 있으면 그것을 쓴다(key 를 빼고 부르면 있는 key 를 알려 준다).

## 커밋

한 작업을 끝에 한 번에 커밋하지 않는다. 뜻이 갈리는 단계마다 나눠 커밋하고, 세부는 커밋이 맡는다. PR 본문은 그것을 요약한다.

- 나누는 자리: 실패하는 테스트(`red` 를 기록하고 그 실패 이유가 아직 구현이 없어서인 것을 읽은 뒤), 구현(크면 뜻이 갈리는 데서 더 나눈다), 막는 지적 하나를 고친 것, 모아 고친 사소한 지적.
- 메시지에는 무엇을 왜 바꿨는지 쓴다. 고른 것과 그 이유도 여기에 적는다.
- 고친 커밋이 생기면 green 과 리뷰가 낡으니, 리뷰를 남긴 뒤에는 고칠 것이 있을 때만 커밋한다. 사소한 지적은 더한 테스트까지 한 커밋으로 모은다(`stages/review.md` 8번).
- 메시지 형식, 브랜치, 병합 방식은 그 레포의 규칙을 따른다.
