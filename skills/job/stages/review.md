# 코드 리뷰

PR 을 열기 전에 이 브랜치의 변경을 리뷰한다. 먼저 `job.py review-files <base>` 를 돌린다. 첫 줄이 base 와의 diff 줄 수(더한 줄과 뺀 줄의 합)와 돌릴 축을 알려 준다. 200줄 미만이면 버그 축만 돌리고, 200줄 이상일 때만 명세 축도 돌린다.

1. **버그 축**: `code-review` 스킬을 수준을 적어서 부른다(`medium`). 수준을 빼면 지난번에 쓴 수준으로 돈다. 첫 리뷰는 base 와의 전체 변경을, 다시 하는 리뷰는 앞 리뷰 뒤에 고친 부분을 본다.
2. **명세 축**(200줄 이상일 때만): `review-files` 가 `job.py show` 출력과 diff 를 워크트리 안 `.fade-review/`(git 이 무시하는 폴더)에 써 둔다. 첫 리뷰는 base 와의 전체 변경을, 다시 하는 리뷰는 앞 리뷰 뒤에 고친 부분만 담는다. 어느 쪽인지는 출력의 둘째 줄에 나온다. 앞 리뷰에서 명세 축이 돌지 않았거나 앞 리뷰의 커밋이 사라졌으면(rebase) 전체를 담는다. 계획서 원문을 그 폴더의 `plan.md` 로 쓰고, 세 경로와 diff 가 전체인지 고친 부분인지를 주어 `fade:reviewer` 에이전트를 띄운다.
3. **나눈다.** 막는 지적은 테스트를 깨거나, 운영을 망가뜨리거나, 데이터나 비밀을 잃거나, 완료 기준을 못 채우는 것이다. 그 밖은 사소한 지적이다. reviewer 는 나눠서 돌려주고, `code-review` 의 지적은 이 기준으로 나눈다.
4. **막는 지적을 고친다.** 고칠 때마다 그 문제를 잡는 테스트를 먼저 더해 `red` 를 보고 고친 뒤 `green` 을 돈다. 고친 막는 지적마다 `job.py slip review "<무엇을 잘못했나>"` 로 실수 기록에 남긴다.
5. 고쳤으면 `job.py check` 가 낡았다고 알리는 증거와 직접 써 보기만 마지막 커밋에서 다시 하고(고친 경로에 기대는 것과 경로를 적지 않은 것이다), `green` 을 다시 돌리고, 다시 리뷰한다.
6. 리뷰할 때마다 `job.py review <남은 막는 지적 수> "<요약>"` 으로 남긴다. 사소한 지적, 판단 보류, 고치지 않기로 한 막는 지적(오탐, 범위 밖)과 그 이유는 요약에 적는다. 고치지 않기로 한 것은 수에서 뺀다.
7. 남은 막는 지적이 0 이 되면 PR 단계로 간다. 같은 지적을 두 번 고쳐도 남으면 해결하지 못한 것이니 `job.py stop` 으로 남기고 끝낸다.
