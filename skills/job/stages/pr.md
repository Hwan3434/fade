# PR

리뷰에서 남은 막는 지적이 0 이 된 뒤에 연다.

그 레포의 규칙이 PR 없이 base 에 바로 반영하라고 하면 PR 을 열지 않는다. 반영 직전에 base 를 받아 `job.py check` 를 돌리고, base 를 받으며 커밋이 바뀌었으면 green 과 리뷰, 그리고 `check` 가 낡았다고 알리는 증거와 써 보기를 다시 한 뒤 그 규칙대로 반영한다. 반영한 커밋은 병합 단계의 4번처럼 `job.py merged` 로 남긴다.

1. 되돌릴 수 있는가를 `job.py door one-way|two-way "<이유와 영향 범위>"` 로 남긴다. 한쪽 문(one-way)은 병합하면 되돌릴 수 없는 변경이다. 예: 데이터 삭제나 마이그레이션, 배포, 공개 API 나 저장 형식 변경. revert 로 돌아가는 변경은 양쪽 문(two-way)이다. 한쪽 문이면 병합은 사용자가 정한다.
2. 커밋하고 push 하고, 브랜치에 PR 이 없으면 연다. 본문 맨 앞에 결과를 쓰고, 그 아래에 「되돌릴 수 있는가」 칸(한쪽 문·양쪽 문, 영향 범위)을 쓰고, 그 아래에 `job.py show --full` 의 출력을 붙인다(로그 파일은 이 맥에만 있어서 내용째 붙인다). 형식과 제목은 그 레포의 규칙을 따른다.
3. `job.py pr <PR 주소>` 로 기록한다.
4. CI 가 끝날 때까지 본다. 레포에 CI 가 없으면 없다고 보고에 적는다. 데스크톱 앱이면 PR 상태 도구로, CLI 면 `gh pr checks <번호> --watch` 로 본다.
5. CI 가 실패하거나 충돌이 나거나 리뷰 댓글이 있으면, CI 실패는 `job.py slip ci "<무엇을 잘못했나>"` 로 실수 기록에 남기고, 테스트부터 고치고 green 과 리뷰, 그리고 `job.py check` 가 낡았다고 알리는 증거와 써 보기를 마지막 커밋에서 다시 한 뒤 push 한다. 같은 실패를 두 번 고쳐도 남으면 `job.py stop` 으로 남기고 끝낸다.
