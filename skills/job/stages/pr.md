# PR

리뷰에서 남은 막는 지적이 0 이 된 뒤에 연다.

그 레포의 규칙이 PR 없이 base 에 바로 반영하라고 하거나 레포에 원격이 없으면 PR 을 열지 않는다. 반영 직전에 base 를 받아(원격이 없으면 받을 것이 없으니 건너뛴다) `job.py check` 를 돌리고, base 를 받으며 커밋이 바뀌었으면 green 과 리뷰, 그리고 `check` 가 낡았다고 알리는 증거와 써 보기를 다시 한 뒤 그 규칙대로 반영한다. 반영한 커밋은 병합 단계의 4번처럼 `job.py merged` 로 남긴다.

1. 되돌릴 수 있는가를 `job.py door one-way|two-way "<이유와 영향 범위>"` 로 남긴다. 한쪽 문(one-way)은 병합하면 되돌릴 수 없는 변경이다. 예: 데이터 삭제나 마이그레이션, 배포, 공개 API 나 저장 형식 변경. revert 로 돌아가는 변경은 양쪽 문(two-way)이다. 한쪽 문이면 병합은 사용자가 정한다.
2. push 하고, 브랜치에 PR 이 없으면 연다. 본문은 사람이 읽는 요약이다. 세부는 단계마다 나눈 커밋의 메시지가, 기록 전문은 보고 단계에서 다는 PR 의 기록 댓글이 맡으니, 본문에 명령 출력이나 기록을 붙이지 않는다. 본문에는 아래만 이 차례로 쓴다. 형식과 제목은 그 레포의 규칙을 따른다.
   - 결과: 무엇이 바뀌었나. 중요한 것부터 몇 줄로 쓴다.
   - 되돌릴 수 있는가: 한쪽 문·양쪽 문과 영향 범위.
   - 고른 것과 이유: 중요한 것만. 나머지는 커밋 메시지에 있다. 없으면 「없음」.
   - 고치지 못한 것: 이유와 함께. 없으면 「없음」.
   - 완료 기준: 기준마다 결과 한 줄. 실제 값은 자기 말로 짧게 쓰고, 출력은 옮기지 않는다.
3. `job.py pr <PR 주소>` 로 기록한다.
4. CI 가 끝날 때까지 본다. 레포에 CI 가 없으면 없다고 보고에 적는다. 끝날 때까지 막고 기다리는 명령(`gh pr checks <번호> --watch`)을 명령 도구의 시간 제한을 늘려 돌린다. 그러면 알림을 기다리며 턴을 끝내지 않아도 된다.
5. CI 가 실패하거나 충돌이 나거나 리뷰 댓글이 있으면, CI 실패는 `job.py slip ci <key> "<무엇을 잘못했나>"` 로 실수 기록에 남기고, 테스트부터 고치고 green 과 리뷰, 그리고 `job.py check` 가 낡았다고 알리는 증거와 써 보기를 마지막 커밋에서 다시 한 뒤 push 한다. 같은 실패를 두 번 고쳐도 남으면 `job.py stop` 으로 남기고 끝낸다.
