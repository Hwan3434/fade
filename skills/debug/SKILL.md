# debug — 디버깅 순서

순서대로 간다. 각 단계의 조건이 채워지면 다음 단계로 간다.

1. **실패하는 명령 하나를 만든다.** 이 버그에서 실패하고, 몇 초 안에 끝나고, 매번 같은 결과를 내고, 사람 없이 도는 명령이다. 사용자가 말한 증상 그대로를 판정한다. 이 레포에 검증 스킬이 있으면 그것으로 재현한다. 없으면 실패하는 테스트, 고정 입력으로 도는 스크립트, 저장해 둔 요청의 재생 순으로 시도한다. 가끔만 나는 버그는 반복 실행으로 재현율을 올린다. 명령을 한 번 돌려 실패 출력을 보인 뒤에 2단계로 간다. 만들 수 없으면 시도한 것을 적고, 재현 환경이나 로그를 사용자에게 요청한다.
2. **재현 조건을 줄인다.** 입력, 설정, 단계를 하나씩 빼며 명령을 다시 돌린다. 남은 것 가운데 하나라도 빼면 통과할 때 3단계로 간다.
3. **가설을 3~5개 세워 순위를 매긴다.** 가설마다 "X 가 원인이면 Y 를 바꾸면 사라진다"는 예측을 붙인다. 확인하기 전에 사용자에게 보여 준다. 사용자가 자리에 없으면 순위대로 진행한다.
4. **예측을 하나씩 확인한다.** 한 번에 하나만 바꾼다. 디버거와 가설을 가르는 자리의 로그를 쓴다. 디버그 로그에는 고유 접두어(`[DEBUG-a4f2]`)를 붙인다. 성능 문제는 기준 측정값을 먼저 잡는다. 예측이 맞은 가설이 하나로 좁혀지면 5단계로 간다.
5. **회귀 테스트를 쓰고 고친다.** 버그가 실제로 일어나는 자리에서 실패하는 테스트를 쓰고, 실패를 본 뒤 고치고, 통과를 본다. 그런 자리가 없으면 그것을 구조 문제로 보고한다. 줄이기 전의 원래 상황으로 1단계 명령을 다시 돌려 통과를 본다.
6. **정리한다.** 접두어로 찾아 디버그 로그를 지우고, 임시로 만든 파일을 지운다. 맞았던 가설을 커밋이나 PR 본문에 적는다.

명령, 출력, 로그를 보일 때 비밀 값은 `<REDACTED>` 로 가린다.
